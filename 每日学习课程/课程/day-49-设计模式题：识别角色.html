小白讲解

角色名只是线索

Context、Strategy、Observer、Factory等常提示模式，但仍要看关系。Context持有可替换算法多为策略；Subject维护观察者集合并notify多为观察者。

填代码顺序

先确定抽象角色和具体角色，再看客户依赖谁，最后填创建、注册、调用等语句。答案要与题干给出的命名一致。

记忆主线
先意图，后角色，再关系，最后语法；不能只凭一个类名猜。

跟着做一道例题

观察者角色

WeatherStation维护Displays列表，数据变化后逐个update，是什么模式？

  1. 一个主题维护多个订阅对象。
  2. 主题状态变化后主动通知全部订阅者。
  3. 这是一对多依赖。

答案：观察者模式；WeatherStation是主题，Displays是观察者。

下午题 · 代码案例

可切换通知渠道的设计

interface Sender { void send(String message); }
class MailSender implements Sender { ... }
class SmsSender implements Sender { ... }
class NoticeService {
    private Sender sender;
    NoticeService(Sender sender) { this.sender = sender; }
    void notify(String text) { sender.send(text); }
}
  1. 该结构体现什么模式？
  2. Sender、MailSender、NoticeService分别是什么角色？
  3. 增加微信渠道应怎样修改？
  4. 它遵循了哪项重要设计原则？
展开采分点答案

① 策略模式。

② 抽象策略、具体策略、上下文。

③ 新增实现Sender的WeChatSender，客户端注入即可，原有上下文不必修改。

④ 开闭原则和依赖倒置原则：面向抽象扩展新策略。
